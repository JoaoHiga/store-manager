# Proposal: Inventory Foundation — Product Catalog & Stock

## Intent

Bootstrap the store-manager inventory app end-to-end: give the owner a working product/category catalog with stock quantities, backed by a Spring Boot REST API (Hexagonal, multi-module Maven) and a React SPA, so the family cellphone shop can start tracking its inventory instead of having nothing at all.

## Scope

### In Scope
- `Category` and `Product` domain entities (single generic `Product` schema, no per-category fields)
- CRUD for categories and products (create/edit/list/delete, filter by category)
- Plain `stockQuantity` field per product
- Spring Boot backend: multi-module Maven (`application` + `infrastructure`), Hexagonal Architecture
- React SPA: Vite, plain JavaScript, atomic design + container/presentational, TanStack Query
- End-to-end wiring (frontend calling the real backend API)

### In Scope (added during PR5)
- Product reactivation (`PATCH /api/products/{id}/activate`) — a real gap noticed manually testing the deactivate flow: the spec only had a one-way soft delete, and a shop needs to bring a discontinued product back. Small enough to complete this change rather than open a new one; scheduled as PR6.

### Out of Scope (also noted for a future change)
- **UX feedback for mutations** (create/edit/deactivate/reactivate) — currently a row just disappears/appears with no confirmation toast. The filtering itself is correct (an inactive-view row leaving when reactivated is intentional), but the lack of feedback makes success indistinguishable from a silent failure. Noticed while testing PR6; deferred rather than folded in.
- Stock-movement ledger / audit trail (deferred to a follow-up change)
- Low-stock alerts, reports
- **Sales & invoicing (`ventas`/`facturación`)** — deferred to a dedicated future change. Explicitly discussed with the user: sales needs the stock-movement ledger (also deferred) to decrement stock traceably, and "facturación" may mean legally-compliant electronic invoicing (country-specific fiscal integration, e.g. AFIP/DIAN/SAT/SII) — a materially bigger, separate problem from recording a sale. Building it now, before the catalog even ships, would be scope creep on top of an unproven foundation.
- Authentication/authorization (deferred — single-owner use for now)
- Per-category custom attributes

## Capabilities

### New Capabilities
- `product-catalog`: category and product management — CRUD, filtering by category, stock quantity tracking

### Modified Capabilities
- None (greenfield — no existing specs)

## Approach

Backend: multi-module Maven — `application` module (domain entities, ports, use cases, zero Spring dependency) + `infrastructure` module (Spring Boot, JPA adapters, REST controllers/DTOs), enforcing the Hexagonal boundary at the build level. Frontend: Vite-scaffolded React SPA, atomic design components, TanStack Query for server state against the REST API. Confirmed by research (`research.md`) over a single-module alternative and a TypeScript-first alternative.

## Data Model (draft — finalized in `sdd-design`)

**Category**: `id`, `name`, `description` (optional).

**Product**: `id`, `sku` (String, unique — **auto-generated by the app for now**, but the field is designed to accept manual/barcode input later without a schema change), `name`, `description` (optional), `categoryId` (FK), `brand` (optional), `costPrice` (BigDecimal — enables margin calculation later), `salePrice` (BigDecimal), `stockQuantity` (Integer), `active` (Boolean — **soft delete**: "deleting" a product sets `active: false` instead of removing the row, so a future stock-movement ledger can still reference it), `createdAt`/`updatedAt`.

Confirmed with the user: soft delete via `active`, `sku` auto-generated today with future manual/barcode entry in mind.

## Risks

| Risk | Likelihood | Mitigation |
|---|---|---|
| No workspace test command exists yet — Strict TDD currently blocked | High (certain today) | First `sdd-apply` batch scaffolds real `mvn test` / `npm test` before other work |
| Change may exceed the 400-line PR budget | Medium | `auto-chain` delivery strategy already selected; `sdd-tasks` slices by backend / frontend / wiring |
| Multi-module Maven adds a new build concept | Low | User's Java strength covers this; explicit confirmed decision from research |

## Rollback Plan

The whole change lives in new modules/files with no existing behavior to break. Revert = delete the new Maven modules and the `frontend/` directory, or `git revert` the merge commit(s) — no data migration exists yet to roll back.

## Dependencies

- None external. Requires Java 21+ and Node 20.19+ locally (per research).

## Success Criteria

- [ ] `mvn -pl application,infrastructure test` and `npm test` both run (even minimally) and pass
- [ ] Owner can create a Category and a Product, see it listed, edit it, and deactivate it (soft delete) — from the React UI, through the real API
- [ ] Hexagonal boundary is enforced: the `application` module's `pom.xml` has zero Spring/framework dependency
